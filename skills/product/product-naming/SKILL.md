# product-naming: プロダクト名の案を出して決める

プロダクトの働きと命名の方針から名前の候補を作り、重なりを確かめ、比較表で比べ、
ユーザーが 1 つに決めるまで繰り返す。決まったら経緯をファイルに記録して終える。

## 範囲

受け持つのは、方針の確認、候補出し、重なりの確認、比較、決定の記録まで。

改名の作業（文書・設定・リポジトリ名の置き換え）は受け持たない。既存の名前を変える場合は、
置き換える対象の一覧を記録に入れて終える。

商標とドメインは確かめない。確かめていないことを、質問と記録の両方に書く。

## 入力

次の 2 つを、引数か会話から受け取る。足りなければ訊く。

- 製品の働きが分かる文書の場所（コンセプト文書、README、決定の記録など）
- 命名の方針（重なりを避けたい範囲、名前から伝えたいこと、長さや文字の好み、言語の指定など）

ほかのスキルや作業の途中から呼ばれたときは、そこまでの決定の記録も材料にする。

## 手順

### 1. 材料を読む

文書から次を読み取る。推測で補わず、読み取れないものは手順 2 で訊く。

- 製品が何をするか（働き）。複数あれば、中心の働きと周辺の働きを分ける
- 誰が使うか、どう配るか（言語、パッケージレジストリ、コマンド名として打つか）
- 文書がすでに使っている比喩や、今の名前の由来
- 既存の名前を変える場合は、今の名前が出てくる場所の種類（設定ファイル名、サブコマンド、
  環境変数、文書名、リポジトリ名など）

### 2. 方針の読みを確かめる

候補を作る前に、次の 3 点を示して、合っているかを訊く。ここを飛ばさない。

- 命名の方針をどう読んだか。抽象的な方針（「UNIX 哲学に合う」など）は、名前の何を縛るのかを
  具体的に言い直す。読み方が複数あれば、どれを採ったかを書く
- 名前で言いたい製品の働き。中心の働きを 1〜3 個
- 重なりを確かめるパッケージレジストリ。配布のしかたから選び、決められなければ訊く

方針の読みを外したまま候補を出すと、候補ごと作り直しになる。「短いこと」を優先した候補が、
実際には「意味を連想できること」を求められていて外れる、という形で起きる。

### 3. 候補を作る

次の種類を、最初から混ぜて作る。方針で種類が指定されていれば、その種類に絞る。

- 日本語のローマ字（例: 見届け → `mitodoke`）
- 英単語
- 英単語を組み合わせた造語、一部を重ねた造語（例: trace + cascade → `trascade`）
- 日本語と英語以外の言語の語（ラテン語、ドイツ語など）
- 言語をまたいだ組み合わせ（日本語と英語、ほかの言語と英語など）

作るときの注意:

- 数に上限は置かない。重なりの確認で大半が外れるので、最初から数十個を作る
- 短い実在の語（4〜5 文字の英単語など）は、ほぼ確実に既存のパッケージか、スターの多い
  リポジトリと重なる。造語や、あまり使われない語を多めに入れる
- 候補ごとに、元の語、意味、名前が言う製品の働きを控える。比較表でそのまま使う
- 小文字の英数字にする（パッケージ名、コマンド名としてそのまま使える形）

### 4. 重なりを確かめる

同梱のスクリプトで確かめる。コマンドを自分で組み立て直さない。

```bash
UV_PROJECT_ENVIRONMENT="$HOME/.cache/uv-venvs/product-naming" uv run --project "<skill-dir>" python "<skill-dir>/scripts/name_check.py" --registry crates,npm,pypi 候補1 候補2 ...
```

- `<skill-dir>` は、この SKILL.md があるディレクトリの絶対パスに置き換える。エージェントが
  スキルを読み込んだときに示されるスキルのディレクトリを使い、特定のエージェントの環境変数
  には頼らない。パスと環境変数の展開は、空白を含んでも分かれないようにダブルクォートで囲む
- `UV_PROJECT_ENVIRONMENT` は必ず付ける。スキルのディレクトリは読み取り専用の場所に置かれる
  ことがあり、その下に venv を作れない
- `--registry` には、手順 2 で決めたレジストリだけを渡す（`crates`・`npm`・`pypi`、
  どれも要らなければ省く）。repology と GitHub は、指定に関係なく確かめる
- GitHub の確認は `gh` を呼ぶ。`gh auth status` が通る状態で実行する
- 候補ごとに 2 秒待つ（GitHub の検索 API の制限に合わせた既定値）。候補が多いときは、
  時間がかかる前提で、バックグラウンドで実行するか、20 個ほどに分けて実行する
- 出力は 1 候補 1 行の TSV。そのまま記録のファイルに貼る

列の読み方:

| 列 | 意味 |
|---|---|
| `repology` | 同名のパッケージを持つリポジトリ（Linux ディストリビューション、Homebrew、nixpkgs など）の数 |
| `crates`・`npm`・`pypi` | `free`（同名なし）か `taken`（同名あり） |
| `gh_user` | 同名の GitHub アカウント。`User`・`Organization`・`none` |
| `gh_inname_total` | 名前に候補を含むリポジトリの総数 |
| `gh_exact` | 上位 100 件のうち、名前が完全に一致するリポジトリの数 |
| `gh_exact_maxstars`・`gh_exact_top` | そのうち最大のスター数と、そのリポジトリ |

`error:<理由>` の列は確かめられていない。空きとして扱わず、原因を直して、その候補だけ
もう一度実行する。終了コードは、error の列があれば 1、引数の誤りは 2。

スクリプトが対応していない配布先（RubyGems、Docker Hub など）では、そのレジストリで同名を
確かめる方法をその場で調べて確かめ、結果を同じ表に列として加える。Go のモジュールと JSR の
パッケージは、名前だけでは識別されない（パスやスコープが付く）ので、GitHub の確認で足りる。

重なりの重さは、数字だけで決めない。同名のアカウントが 1 つあるだけなら、organization を
その名前で作れないだけで、リポジトリは自分のアカウントの下に置ける。スターの多い同名の
リポジトリや、配布先のレジストリの `taken` は重い。

候補の名前は、レジストリ・GitHub・Web 検索に送られる。公開前の名前を外に出したくないと
ユーザーが言っている場合は、確かめる前に相談する。

### 5. 同じ分野の近い名前を探す

パッケージと GitHub の確認を通った候補のうち、選択肢に残すものについて、Web 検索で同名と、
綴りの近い製品を探す。

- クエリの形: `"<名前>" software`、`"<名前>" app OR software OR tool`。日本語由来の名前は、
  かな・カタカナの読みでも検索する
- 見るのは、同名の製品があるかと、同じ分野に綴りの近い製品があるか。パッケージ名が空いて
  いても、同じ分野の製品と 1 文字違い、という重なりはここでしか見つからない
- 日本語と英語以外の言語の語を使った候補は、その言語での意味と、ほかの主要な言語での
  不都合な意味を、検索で確かめられる範囲で確かめる。確かめきれないことは、そう書く

### 6. 比較表を付けて訊く

候補は毎回、比較表を付けて示し、推奨を 1 つ添える。選択肢と推奨だけで訊かない。
名前は好みで決まる部分が大きく、推奨がそのまま採られることは少ない。ユーザーが自分で
比べられる材料を、最初から同じ観点で出す。

比較表の観点（方針から加える。方針に無い観点を重く扱わない）:

| 観点 | 書くこと |
|---|---|
| 名前が言う働き | 手順 2 で確かめた働きのうち、どれを言い、どれを言わないか |
| 綴りと読み | 書き違えやすさ、読み方が 1 つに決まるか、別の語を連想させないか |
| その言語を知らない人への伝わり方 | 伝わる、手がかりがある、伝わらない |
| 重なり | 手順 4 と 5 の結果。「なし」か、何と重なるか |
| 長さ | 文字数 |

質問に入れるもの:

- 選択肢は 4 案まで。表には、選択肢にしなかった有力な候補も載せる
- 推奨 1 つと、その理由。推奨が自分の判断で、文書に根拠が無いところは、そう書く
- 確かめた事実（どこを確かめたか、いつ確かめたか）と、確かめていないこと（商標、ドメイン、
  確かめきれなかった言語での意味）
- 既存の名前を変える場合は、名前を変えると置き換わるものの種類
- 外した候補を表に入れないときは、外した理由を 1 行で書く

AskUserQuestion が使える環境では、質問の本文を示したうえで AskUserQuestion で訊く。
ユーザーが選択肢に無い名前や、条件付きの回答を書けるようにする。

### 7. 決まるまで繰り返す

ユーザーが 1 つに決めるまで、回答に合わせて手順 3〜6 を繰り返す。回数の上限は置かない。

- 候補の追加を求められたら、残す候補はそのまま持ち、求められた方向の候補を手順 3 から作る。
  追加した候補も、手順 4 と 5 を通してから示す
- 候補を外す理由を言われたら、その理由を方針の読みに反映する。同じ理由で外れる候補を、
  次の回に出さない
- 2 つに絞られたら、決選投票にする。それぞれの弱点を、表に並べて書く
- 「ある観点を外して比べ直して」と言われたら、その観点を加点に使わないとどう読んだかを示し、
  外した候補も含めて比べ直す
- ユーザーが推奨と違う名前に決めたら、それが決定。理由を訊き出そうとせず、その名前の代償
  （伝わらない読み手がいる、など）を記録に書く

決まったら、決まった名前だけで、もう一度 Web 検索をする（名前だけのクエリと、読みのクエリ）。
新しい重なりが見つかったら、決定を記録する前にユーザーに伝える。

### 8. 決定を記録する

記録はファイルに残す。候補が増えると、確認結果を会話だけに置いたままでは、あとの回で
確かめ直すことになる。重なりの確認結果は、手順 4 を実行するたびに追記する。

書く場所は、次の順で決める。

1. ユーザーか、呼び出した側が指定した場所
2. 作業している環境に、一時的な成果物や調査結果の出力先の決まりがあれば、その決まり
3. どちらも無ければ、書く前に場所を訊く

記録に入れるもの:

- 確かめた方針の読みと、名前で言いたい働き
- 重なりの確認結果の表（確かめた日付つき。回ごとに分けて、すべての候補を残す）
- Web 検索で見つかった、同名または綴りの近い製品
- 質問ごとの、推奨と回答（ユーザーの言葉は原文のまま）
- 外した候補と理由
- 決定した名前、由来、選んだ理由、代償
- 確かめていないこと（商標、ドメインなど）
- 既存の名前を変える場合は、置き換える対象の一覧（設定ファイル名、サブコマンド、環境変数、
  文書名と本文、リポジトリ名、パッケージ名など。リポジトリを検索して、今の名前の出現箇所から
  作る）。新しい製品に名前を付ける場合は要らない

## スクリプトを直すとき

`scripts/name_check.py` を変えたら、テストを全件成功させる。

```bash
UV_PROJECT_ENVIRONMENT="$HOME/.cache/uv-venvs/product-naming" uv run --project "<skill-dir>" pytest
```

テストは外部の API と `gh` を呼ばない。レジストリを加えるときは、`REGISTRY_URLS` に
「同名があれば 200、無ければ 404 を返す URL」を加え、テストを足す。
