# 工程別 定性チェックリスト

test-reviewer サブエージェントがレビュー時に適用する観点。**該当工程の区分 + 共通観点** を
使う。機械検査（存在・必須セクション・空欄・ID 突合）は review-check.sh が済ませているので、
ここでは **機械では判定できない「内容の正否」** に集中する。

## plan（テスト計画）

- 完了基準（exit criteria）が **計測可能** か: 数値・判定手段・取得元が読み取れ、後続の
  test-monitor / test-report がそのまま参照できる形になっているか。
- 各リスクに発生可能性・影響度の **根拠（調査事実）** があり、実在性が検証されているか
  （実際には到達しない防御的分岐を実リスクに計上していないか）。
- テストアプローチがリスク評価と紐づいているか（高リスク領域の重点が読み取れるか。
  リスクと無関係な重点配分になっていないか）。
- スコープ外が **理由つき** で明記されているか。実行に必須の依存がスコープ内に含まれているか。
- 開始基準（entry criteria）が現実に確認可能か。

## analyze（テスト分析）

- テストベース（仕様・test-plan のスコープ）の主要項目に対応するテスト条件が揃っているか
  （**抜けの探索**。機械検査は ID の対応しか見ない）。
- 各条件が「何を検証するか」の抽象レベルで書かれ、粒度ガードを守っているか
  （同値クラスの行列挙・期待結果の埋め込み・検証手段の混入 = 設計への踏み込みがないか）。
- 優先度が test-plan のリスク評価と整合しているか（高リスクに対応する条件が低優先度に
  なっていないか）。
- 「対応テストベース」の参照先（仕様の章・コード箇所）が実在し、条件の根拠として妥当か。

## design（テスト設計）

- 各ケースが対応するテスト条件の **意図を検証できる** 内容か（ID が繋がっていても中身が
  条件とずれていないか）。
- 採用技法のカバレッジ基準を実際に満たしているか（境界値なら各境界の内外、デシジョン
  テーブルなら全ルール、等）。意図的な省略に理由があるか。
- 期待結果が仕様から確定した値・状態で書かれているか（「正しく動く」のような曖昧な期待や
  未確定値が残っていないか）。
- 自動/手動の区分に判定基準（どの実行手段があるから自動か）が設計書に残っているか。

## implement（テスト実装）

- `test-case.md` の全ケースが区分どおりに具体化されているか（ケースと実装の対応が
  追跡できるか）。
- テストに **検証力** があるか: アサーションが期待結果を実際に検証しているか、実行するだけで
  何も確かめない形骸テストになっていないか。
- テストデータ・テストダブルが妥当か（過剰なモックで対象自体を検証しなくなっていないか、
  ダブルの差し替え対象と理由が明記されているか）。
- 手動手順書は実施者が迷わない粒度か（前提・番号付き手順・入力・期待結果が揃っているか）。

## execute（テスト実行）

- 全ケースについて期待結果と実際結果が **対で** 記録されているか（実際値が「失敗した」で
  なく観測値・エラー内容で書かれているか）。
- 失敗が欠陥候補として再現手順・期待/実際・影響範囲・暫定重大度つきで整理されているか。
- ブロック/スキップに理由が明記されているか。
- flaky（不安定）疑いの失敗が再実行で切り分けられているか。

## monitor（モニタリング基盤）

- 各メトリクスが test-plan の完了基準と実質的に紐づいているか（対応欄が形式的でないか）。
- 取得元が調査で実在確認されたツール出力か（存在しない出力形式を前提にしていないか）。
- しきい値に定義と根拠があるか。
- 計測が基盤（CI・スクリプト）で自動化される設計か（AI や人の継続監視を前提にしていないか）。

## report（テスト完了レポート）

- test-plan の全完了基準が 1 項目ずつ判定され、根拠の数値が添えられているか
  （判定不能の基準がなし崩しに「達成」扱いになっていないか）。
- 総合判定が基準判定の内訳と整合しているか（未達があるのに「完了」になっていないか）。
- 高リスク領域の消化状況がリスク評価と対応づけられているか。
- 未達時に何が不足で、次に何をすべきかが具体的か。

## 共通観点（全工程に適用）

- **記述スタイル**: 略号・コードネームが定義なしで使われていないか。スキルの実行記録
  （Q&A ログ・所要時間等）が混入していないか。成果物単体で読み返して意味が取れるか。
- **改善提案の運用**: 解消済みの提案が残っていないか。前工程・メモリで既決の事項が
  再掲されていないか。
- **前工程との整合**: 前工程成果物の内容と矛盾する記述がないか（用語・番号・前提のずれ）。
