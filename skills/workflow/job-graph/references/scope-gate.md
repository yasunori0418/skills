# 計画突合ゲート — Phase 4 で PR を計画と突き合わせる

ワーカーの PR を「計画に書かれた変更だけか」で機械判定してから凍結確認・次段起動へ進む手順。
判定は `scripts/check_scope.py`（純粋関数 `judge`）で、ワーカーが PR 前に `--base` で行う自己確認と、親が PR 報告後に `--pr` で行う本ゲートは同じ基準を使う。

## なぜ突合を親が別途行うか

2026-08-25〜26 の運用で、4 PR 全てに計画外のリファクタリング（型化・関数抽出・命名変更）が混入し全撤回になった。原因は 3 つが重なったこと:

- ワーカーは review-converge の指摘を「品質改善」として取り込み、計画外かどうかを自分では判定できなかった
- 親は「コミット数が計画より多い」ことに気付いたが、commit-plan の「論理単位で都度コミット」を根拠に**許容で流した**（14:14 の裁定）。コミット数の増加は突合のトリガーであって、許容の根拠ではない
- 「範囲内かどうか」の判定を親が自分で行い、ユーザーに問わずに通した。範囲内判定を親自身が行うと仕様変更が既成事実化する（lane-ops の判定基準表の除外リスト）

機械判定（ファイル一覧の完全一致 + 規模上限）を挟むと、この 3 つのどれが起きても FAIL で止まる。

## 手順（PR 報告を受けたら）

1. `[lane-ops:report <id>] PR 作成` を受けたら、まず `verify_lane.sh <branch> <worktree>` で PR の存在・push 同期・未コミット変更を裏取りする（自己申告を信用しない）
2. `plan_orchestration.py` 出力の `VERIFY` 節にある、その task のコマンドを PR 番号を埋めて実行する:

   ```sh
   python3 <SKILL>/scripts/check_scope.py --pr <PR番号> --expected-file <計画のファイル>... --expected-scale <目安>
   ```

3. 末尾の `VERDICT` で分岐する:
   - **PASS** → 凍結確認（PR 後の push が無いこと）へ進み、次段の起動ゲート（`gh pr list --head`）を満たしたと扱う
   - **FAIL** → 下記「FAIL 時の処置」。**次段を起動しない**
   - **SKIP**（期待が無い）→ 機械判定できない。`=== CHANGED ===` を計画と目視で突き合わせ、迷いがあれば FAIL と同じ扱いにする
4. handoff.md の現在地の `突合` 列を更新する（`合格` / `要裁定` / `裁定済み`）

コミット数が計画より多い・review-converge の反復が多かった、という兆候は**突合を省く理由ではなく、必ず突合する理由**になる。

## FAIL 時の処置

- PR は draft のまま凍結を維持する（ワーカーは規約どおり PR 後に実装変更しない。追加 push が見えたら `send_instruction.sh` で止める）
- 次段を起動しない（計画外変更を base に含んだ後段は、撤回時に丸ごと restack になる）
- **ワーカーへ分離・削除の指示を自分で出さない**。何を計画外とみなすか・削るか分離するか承認するかは、lane-ops の判定基準表で「常にユーザー裁定」に当たる
- ユーザーへ次の定型で報告し、裁定を待つ:

  ```
  計画突合 FAIL: <task-id> PR #<番号>
  - 計画外ファイル: <UNEXPECTED の一覧>
  - 規模: 実測 <N> 行 / 目安 <M> 行（上限 <2M>）
  - 選択肢:
    1. 承認して続行（計画外変更を受け入れる。expected_* を更新して再突合）
    2. ワーカーへ分離指示（計画外変更を別コミット/別 PR へ切り出させる）
    3. 計画と expected_* を更新（計画側が漏れていた場合）
  ```

- 裁定が出たら handoff.md の「運用注意・事前裁定」に `裁定: <内容> / 承認: ユーザー確認済み` で記録し、指示があれば `send_instruction.sh` で送る。再突合して PASS になるまで次段は止めたまま

## `check_scope.py` の使い方

| 引数 | 意味 |
| --- | --- |
| `--pr <N>` | PR の変更を `gh pr view --json files` で収集（親用）。`--base` と排他 |
| `--base <ref>` | ローカルの `git diff --numstat <ref>...HEAD`（ワーカーの PR 前自己確認用） |
| `-C <worktree>` | git / gh の実行ディレクトリ |
| `--expected-file <path>` | 計画の変更ファイル（繰り返し。glob 不可。起草基準は `spec.md`） |
| `--expected-scale <N>` | 規模目安。実測（追加 + 削除）が `N × 2` を超えると FAIL |

出力は `=== CHANGED ===`（`tmp_claude/` 除外済みの変更一覧）/ `=== UNEXPECTED ===`（計画に無いファイル）/ `=== SCALE ===`（実測 / 目安 / 上限）と `REASON:` 行、末尾 `VERDICT: PASS|FAIL|SKIP`。終了コードは PASS/SKIP=0・FAIL=1・収集失敗=2。先頭に `WARNING:` があれば、PR のファイル数に対して `files` の取得が足りていない（gh の件数上限）。その分は突合に掛かっていないので、`gh pr diff --name-only` で補う。
