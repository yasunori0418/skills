# plan-template — `tmp_claude/<job>/plan.md` の 6 章テンプレ

plan.md は 2 つの読者を持つ。ワーカーの `/review-converge` が `DIFF_REVIEW_GROUND_TRUTH` として読む
（第 3 章の完了条件・変更対象と第 5 章のスコープ外が「計画に無い変更」の判定材料になる）のと、
`scripts/check_plan_spec.py` が spec.json との整合を機械検査する。後者のため **第 3 章の文法は固定**で、
崩すと偽 FAIL になる。章見出しは `## <番号>. <題名>` で 6 つとも必須。

## テンプレ

````markdown
# 計画: <job>

## 1. 目的・背景

<なぜやるか。入力資料（自由記述 / docs/dev/<対象>/spec.md / issue）の要点>
<入力に REQ-# があれば、ここで全て列挙する（第 3 章の `- 対応要求:` と突合される）>

## 2. タスク一覧と依存グラフ

| id | 概要 | branch | 依存 |
| --- | --- | --- | --- |
| A | <概要> | <branch> | なし |
| B1 | <概要> | <branch> | なし |
| B2 | <概要> | <branch> | B1 |

<起動ウェーブの見込み（wave 0: A, B1 / wave 1: B2）。この章は散文扱いで検査しない>

## 3. タスク詳細

### A: <概要>
- branch: `<branch>`
- 依存: なし
- 対応要求: REQ-01
- 完了条件: <第三者が検証できる条件。テストが通る・コマンドの出力が○○になる等>
- 変更対象:
  ```
  path/to/file.py
  path/to/test_file.py
  ```
- 規模目安: 120 行
- 境界:
  ```
  path/to/**
  ```
- コミット計画:
  1. `feat(scope): <メッセージ>`
  2. `test(scope): <メッセージ>`

### B2: <概要>
- branch: `<branch>`
- 依存: `B1`
…

## 4. 事前裁定

- 裁定: <内容> / 承認: ユーザー確認済み

## 5. スコープ外

- <検討して落としたもの。ワーカーが「ついでに」やりそうなことほど書く>

## 6. 引き渡し

- 起動: `/job-graph tmp_claude/<job>/plan.md`
- 親の permission mode: acceptEdits 等の明示モード
````

第 4 章は 1 行 1 裁定の固定様式で、上の例のような裁定行か `- 該当なし` 以外の行（注記・散文）を
置くと ERROR になる。第 6 章は issue を出したとき `create_issues.py` が URL 行を末尾に追記する。

## 各章の書き方

### 第 1 章: 目的・背景

入力資料の要点と、grilling で固めた「何のためにやるか」。**入力資料に `REQ-#` があるときは
ここに全て列挙する**。`check_plan_spec.py` は第 1 章の REQ-# が第 3 章のどの task にも現れなければ
WARNING を出す（取りこぼしの検出）。

### 第 2 章: タスク一覧と依存グラフ

人が読むための一覧。表の形は自由で検査しない（依存の正は第 3 章の `- 依存:`）。
依存の判定基準は job-graph の `references/dependency-analysis.md`。

### 第 3 章: タスク詳細（固定文法）

spec.json の task と 1:1。節見出しは `### <id>: <概要>`（id は英数字・`_`・`-`）。小見出しは
次の 7 つが**全て必須**（順序は自由、`- <label>:` の形）:

| 小見出し | 書式 | spec との対応 |
| --- | --- | --- |
| `- branch:` | `` `<branch>` `` | `branch`（完全一致） |
| `- 依存:` | `なし` または `` `B1`, `B2` `` | `depends_on`（集合一致） |
| `- 完了条件:` | 散文（1 行でも複数行でも） | `prompt` の完了条件部分（検査しない） |
| `- 変更対象:` | 直後にコードブロック、1 行 1 パス。無ければ `なし` | `expected_files`（集合一致） |
| `- 規模目安:` | `<整数> 行` | `expected_scale`（一致） |
| `- 境界:` | 直後にコードブロック、1 行 1 glob。無ければ `なし` | `boundary`（集合一致） |
| `- コミット計画:` | 番号付きリスト（commit-plan スキル準拠） | `prompt` に載せる（検査しない） |

任意の小見出し: `- 対応要求: REQ-01, REQ-02`（REQ-# の引き継ぎ。第 1 章との突合に使う）。

書き方の注意:

- **変更対象は glob 不可**。リポジトリルート相対の実パスをそのまま書く（`check_scope.py` が完全一致で
  照合する）。lockfile・生成物・`plugin.json` の登録配列など「必ず巻き添えになるファイル」も列挙する
  （基準は job-graph `references/spec.md`）。stacked の後段は、その段で触るファイルだけ
- **境界に `tmp_claude/**` を書かない**。job-graph が自動付与する。書いても検査からは除外されるが、
  書く意味が無い
- **規模目安は追加 + 削除の合計行数**（テスト込み）。実測が 2 倍を超えると計画突合が FAIL するので、
  盛りすぎず削りすぎず
- **完了条件は「第三者がテストを書けるか」を通過基準にする**（feature-spec と同じ）。曖昧語
  （「適宜」「必要に応じて」「等」）を使わない。ワーカーはここだけを見て終了判断する

### 第 4 章: 事前裁定

ワーカーの選択ダイアログや裁定要求に親が即答するための判断材料。様式は job-graph
`references/handoff.md` と同じで、**1 行 1 裁定、承認の併記が必須**:

```
- 裁定: <内容> / 承認: ユーザー確認済み
```

- job-plan は対話で確定させるので `承認: 親のみ（未確認）` は書けない（`check_plan_spec.py` が ERROR）
- 何を裁定として書くべきかは lane-ops の判定基準表（`lane-ops/SKILL.md` の「承認代行の判定基準」）の
  「常にユーザー裁定」行が正: 仕様の解釈変更・検査/バリデーションの緩和・計画に無い型/関数/enum の
  追加・「据え置く」と明記した箇所の変更。**ここで再定義しない**
- 無ければ `- 該当なし` と明記する（空のままにしない）。ただし「該当なし」で済むのは、grilling で
  裁定候補を洗ったうえで本当に無いときだけ。feature-spec 入力（REQ-# あり）のジョブで該当なしに
  なることは稀
- 覆った裁定は削除せず `/ 撤回済み（<日時 JST>）` に更新して残す

### 第 5 章: スコープ外

検討して落としたものを明示する。空だと WARNING。ここは手放し運用中に親・ワーカー・review-converge
が「計画外の変更か」を判定する材料になるので、**ワーカーが善意でやりそうな隣接作業ほど書く**
（「ついでのリファクタ」「関連するが今回触らないモジュール」「後続 PR に回す項目」）。

### 第 6 章: 引き渡し

`/job-graph tmp_claude/<job>/plan.md` の起動コマンドと、親を動かす permission mode の注意。
issue を出したときは `create_issues.py` が `- epic: <URL>` / `- sub-issue: <id> → <URL>` を末尾に追記する
（改訂時の `--epic` 番号はここから読む）。
