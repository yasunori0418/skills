# レンズ: 仕様適合・欠落検出 (spec)

このファイルは「何を見るか」と観点固有の severity 補正のみを定義する。
severity 体系・実害ベースの貫通原則・2 パス自己検証は本体(diff-reviewer.md)に一元化されており、それをそのまま適用する。

## このレンズの向き(他レンズとの決定的な違い)

既存レンズは diff に**書かれたもの**を見て「悪い変更」を見つける。このレンズは宣言された仕様・テストケースを基準に
diff に**書かれていないもの**を見て「**あるべき変更の欠落**」を見つける。方向が逆であることを常に意識する。

したがって「不要なコードがある」「過剰だ」という削減方向の指摘はこのレンズの守備範囲ではない
(それは design レンズの領分であり、かつ後述の禁止事項に該当しうる)。

## 判断基準(グラウンドトゥルース)

manifest の `== GROUND_TRUTH ==` 節の**確定分**を、レビュー開始前に必ず Read する:

- `docs/dev/<対象>/spec.md`: 機能要求(REQ-#)・非機能要求(NFR-#)・受け入れ条件(AC-#)・スコープ外
- `docs/dev/<対象>/basic-design.md`(あれば): 機能一覧(REQ-# 参照)・モジュール構成・インターフェース・データフロー
- `docs/test/<対象>/test-case.md`(あれば): テストケース(CASE-#)と期待結果
- `明示指定(DIFF_REVIEW_GROUND_TRUTH)` に並ぶファイル: 規定パス外に置かれた仕様・設計・テストケース。
  ファイル名や見出しから役割(仕様 / 設計 / テストケース)を判断して上と同じ扱いにする。
  ID 体系が REQ-# / CASE-# でない場合は、その文書が使っている見出し・項番をそのまま根拠として引く

節に列挙が無いファイルを推測で探しに行かない。節そのものが無ければこのレンズは起動されない。

`候補(規定パス外...)` として並ぶパスは**未確定**であり、判断基準に使わない(採否はオーケストレータが
ユーザーに確認し、採用分は「明示指定」として渡し直される)。候補しか無い状態でこのレンズが起動されることは無いが、
もし候補のみの manifest で起動されたら、その旨を報告して指摘は出さない。

対象が複数列挙されている場合、diff の変更パスと各対象の記述を突き合わせ、**diff が触っている対象に絞って**精読する
(全対象を無差別に読まない。コンテキスト規律は本体の規定に従う)。

## 見るもの 1: 宣言された REQ / CASE の未充足

diff が対象とする REQ-# / CASE-# を特定し、宣言された挙動が実装に現れているかを一つずつ突合する。

- 実装が REQ の主要な振る舞いを満たしていない(条件分岐の欠落・エラー時挙動の未実装・
  宣言された出力項目の欠落など、**受け入れ条件が現状の diff では満たせない**): **must**
- REQ の一部(周辺の細目・任意項目)が未実装で、AC には抵触しない: **want+**
- CASE-# の期待結果が実装の挙動と食い違う(テストを通すと落ちる構図が読める): **must**
- 実装はあるが対応する CASE-# のテストが diff に無い: **want+**
  (テスト設計の網羅性そのものは test レンズの領分。ここでは「宣言済み CASE の実装漏れ」だけを見る)

指摘には必ず**根拠となる ID**(`REQ-03` / `CASE-07` 等)と、仕様のどの記述に基づくかを 1 文で添える。
ID を挙げられない指摘はこのレンズでは出さない(それは他レンズの指摘である)。

## 見るもの 2: 仕様に無い挙動変更(スコープ外の混入)

diff が仕様で宣言されていない振る舞いを持ち込んでいないかを見る。

- spec.md の「スコープ外」に明記された内容を実装している: **must**
- どの REQ-# にも紐づかない**利用者から観測できる挙動変更**(公開 API・CLI 出力・
  永続データ形式・既定値の変更など)を持ち込んでいる: **want+**。実害(既存利用者の破壊)が
  diff 内で具体化していれば **must**
- 内部リファクタリング・可読性改善など観測可能な挙動を変えないものは**指摘しない**
  (仕様に書かれていないこと自体は問題ではない)

## 見るもの 3: 仕様側の欠陥シグナル

実装が仕様と食い違うとき、誤っているのが実装とは限らない。

- 実装が明らかに妥当で、仕様の記述が古い・矛盾している・曖昧で複数解釈できる場合、
  「仕様の改訂が必要」という向きで **want** を出す(実装を直せという指摘にしない)
- どちらが正しいか判断できない場合は **[PLAUSIBLE]** を付け、両方の解釈を 1 文ずつ示す

## 禁止事項(全レンズ共通ガードのこのレンズ版)

- 仕様・テストケースに根拠のある実装を「過剰・不要」と指摘しない。
  削除・簡略化の提案は、REQ-# / CASE-# に抵触しないことを確認してからに限る
- 仕様に書かれていない改善案をこのレンズから出さない(design / test 等、本来のレンズに委ねる)
- グラウンドトゥルースを読まずに一般論で仕様適合を語らない。Read できなかった場合は
  その旨を報告し、このレンズの指摘は出さない
