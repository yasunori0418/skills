# レンズ: アンチ・オーバーエンジニアリング (yagni)

このファイルは「何を見るか」と観点固有の severity 補正のみを定義する。
severity 体系・kind 体系・実害ベースの貫通原則・2 パス自己検証は本体(diff-reviewer.md)に一元化されており、それをそのまま適用する。

## このレンズの向き(存在理由)

design レンズが「より良い構造への改善」を見るのに対し、このレンズは**逆向き**に「diff が必要以上のものを作り込んでいないか」だけを見る。両方向を 1 体のレビュアーに持たせると構造化方向が勝つことが実運用で確認されている(design レンズ内の YAGNI 観点は 5 周のレビューで一度も過剰実装を指摘できなかった)ため、削る方向を専任で担う。

このレンズの指摘は「diff が導入したものを削れ・縮めろ」であり、対応は diff 内で完結する(= kind は fix。既定モードでも常に報告する)。PR が導入したハーネス・関数・抽象を削る・縮める・インライン化する指摘は、対象がテストハーネスや関数であっても fix であり、常時 improvement パターン(diff-reviewer.md の kind 体系。いずれも**既存**=base 時点で存在するコードが対象)には当たらない。既存コード(diff 外)の簡略化・再設計提案はこのレンズの守備範囲ではない(それは improvement であり、既定モードでは扱わない)。

## 見るもの 1: 未使用・単一使用の汎用化

diff が導入した抽象(enum・trait / interface・ジェネリクス・設定パラメータ・拡張ポイント)ごとに、使用箇所を Grep で数える:

- 使用箇所ゼロ(定義しただけ): **must**
- 「将来使うかもしれない」だけが根拠の引数・フラグ・カスタマイズ点: **must**(誤った抽象は重複より高くつく)
- 使用箇所が 1 つで、直書きと比べて抽象が何も買っていない: **want+**

## 見るもの 2: PR 内で使用されない変更

diff 内で追加・変更されたシンボル(関数・型・メソッド)が、diff 内の他のコードからも既存コードからも参照されていない場合、混入(このタスクに属さない変更)の第一候補として **must** で指摘する。

**計画・仕様に載っていても適用する**。計画自体に混入が紛れ込むことがあり(実事故: 計画に載っていた refactor コミットが PR 内のどのコードからも使われていなかった)、「この PR で使われているか」は計画と独立に検証できる唯一の網。指摘には探索結果(どの範囲を調べて参照が無かったか)を添える。

## 見るもの 3: 独自基盤の持ち込み

- テストハーネス・アサーションフレームワーク・ヘルパー階層など「基盤」の新設: リポジトリの既存手段で同じ検証・処理が書けるなら **must**。書けない場合も基盤の新設がタスクの目的に必須かを疑い、必須性を挙証できなければ **want+**
- 既存ライブラリ・既存ユーティリティで足りる自作実装: **want+**

## 見るもの 4: 周辺同型コードとの防御水準比較

diff が触った箇所と同型の既存コード(同じ trait の他実装・兄弟モジュール・同種の Creator / Handler 群)を 1〜2 個読み、防御・エラー処理・バリデーションの水準を比較する:

- diff だけが一段厚い防御(戻り値の Result 化・追加バリデーション・詳細なエラー分類)を持ち、その必要性が diff の目的から説明できない: **want+**(過剰の一次候補)
- 防御対象の入力が上流(呼び出し元・データ生成側)で既に保証されていることを確認できた場合: **must**(投機的な保険であり、同型コードとの非対称も生む)
- 逆に diff だけが防御が薄い場合はこのレンズでは指摘しない(design / spec レンズの領分)

## 見るもの 5: コミット type シグナル

manifest のコミット一覧に `refactor(...)` / `style(...)` type のコミットが含まれる場合、そのコミットの diff を必ず精読し、見るもの 1〜4 を適用する(過剰混入の一次候補。実事故でも人間レビュアーはコミット type から混入を特定した)。

refactor コミットの存在自体は指摘対象ではない(タスクがリファクタリングなら当然含まれる)。ユーザーの依頼・計画との整合で判断する。

## GROUND_TRUTH との関係

削除・縮小の提案は共通ガードに従う: 仕様・テストケース(REQ-# / CASE-#)に根拠のある実装を「過剰」と指摘しない。GROUND_TRUTH で確認できない場合は **[PLAUSIBLE]** を付けて残す。ただし見るもの 2(PR 内未使用)は、仕様に載っていても「使われていない」という事実が独立に成立するため、探索結果を添えた上で指摘してよい。

**仕様・issue は下限であって上限ではない**。「REQ / issue に書かれていない」だけを根拠に削除を求めない。過剰の根拠は常に見るもの 1〜5 の**実害**(使われない抽象・混入・独自基盤・同型コードとの非対称)で挙証し、「要求外」は補足にとどめる。要求外を過剰の根拠にすると、修正で文や実装が引き締まるたびに基準が下がって次に薄い箇所を指す構図になり、収束しない(README のみの diff で「issue の要求外」を根拠に 5 周回した実例)。

## 散文(ドキュメント)のみの diff

diff がドキュメント・コメント・散文だけのとき、見るもの 1・3・4・5 はコード向けであり適用しない。散文に対する「過剰」は次の 2 つに限る:

- **逐語的な重複**: 同じ主張・同じ手順が同一節内で 2 度述べられている。severity は **nit** に固定する(閾値 `want` の収束ループでは修正対象にならない。読みやすさの好みで周回を消費しない)
- **タスク範囲外の話題**: 依頼・issue の対象と無関係な節・段落の追加(混入)。**want**

次は散文では過剰扱いしない: 失敗モード・前提条件・復旧手順・注意書きの説明、英日など複数言語版で対になっている記述、他レンズ(test / design / spec)が「伝わらない」「誤解を招く」と要求しうる補足。これらは要求に無くても読者の行動を支える記述であり、削れば別レンズが追記を要求して打ち消し合いになる。
